NTRIP Caster 搭建与使用

Caster 是整条链路的「中转站」：基站把 RTCM 推上来，流动站按挂载点把流拉下去，中间由它做鉴权、转发和源表公告。 这一页用我开源的 2RTK NTRIP Caster（Python，Web 管理，Apache-2.0）在 VPS 上从零搭起来， 建好账号和挂载点，最后用基站推流、流动站拉流验证一遍。

2RTK NTRIP Caster NTRIP 1.0 / 2.0 Python 3.9+ TCP 2101 + 5757

Caster 到底在干什么

NTRIP 协议里有三个角色，很容易记混：

Server（源）基站侧，主动推
占用 1 个上行连接
→
Caster（中枢）收 1 份，发 N 份
鉴权 + 源表
→
Client（流动站）主动拉
按挂载点选流

一个 Caster 具体做四件事：

  • 接收与鉴权：验证推流方的凭据，把某一路 RTCM 流绑定到一个挂载点（mountpoint）。
  • 分发：一路流同时发给几十上百个客户端，基站上行带宽只花一份。
  • 公告：维护源表（sourcetable / STR），告诉客户端「我这里有哪些流、在哪、什么格式、什么电文」。
  • 解析：读出流里的 1005 / 1006 电文，反查经纬度、国家、城市，把源表里的位置信息改对——这是 2RTK NTRIP Caster 相比纯转发型 Caster 多做的一步。

负载其实很轻。实测 2000 个并发拉流时 CPU 不到 20%，瓶颈永远在带宽和线路质量上，不在计算。

什么情况下值得自己搭

场景建议
只有一台基站，自己用直接推公共 Caster（比如 本站测试服务器）就够了
几台基站，要给团队分账号自己搭，按挂载点 + 账号做隔离
数据不能公开（厂区、矿区、项目）必须自己搭，公共 Caster 的源表都是公开的
要给客户提供差分服务自己搭，能看在线数、流量、连接日志
基站放在内网，只放出流自己搭在公网 VPS，内网基站主动往上推

为什么用这个 Caster

全程网页管理

加用户、加挂载点、看在线连接、看日志都在浏览器里点，不用改配置文件再重启。

自动生成 STR

建好挂载点直接推流，服务端解析 RTCM 后自己补齐源表字段，不用手写 sourcetable。

SQLite 单文件

账号和挂载点都存在一个 2rtk.db 里，备份就是拷一个文件，换机器两分钟复活。

2000+ 并发

线程池 + 环形缓冲 + 独立发送线程，实测 2000 连接不掉线，CPU 17% 左右。

三种装法

一键脚本（含 systemd + Nginx）、Docker 一条命令、源码 venv 直接跑，按环境挑。

无损升级

update.sh 自动备份、停旧进程、健康检查、失败回滚，数据和账号都不动。

各家授权、免费额度会随版本变，选之前以官方说明为准。这一页只讲 2RTK NTRIP Caster 的完整流程。

先准备一台服务器

最低配置要求不高，但系统版本有一条硬红线：

项目要求说明
系统Debian 11+ / Ubuntu 22.04+CentOS 8+ / RHEL 8+ 也能跑，但没有一键脚本；关键是 Python 3.9+
CPU2 核（x86_64 优先） ARM 也能跑，性能按比例折算
内存2 GB100 并发以下 1 GB 也够
硬盘10 GB主要是日志

Ubuntu 20.04 和 Debian 10 装不上。它们自带 Python 3.8，而依赖里的 pyrtcm==1.1.8 要求 Python 3.9+。 一键脚本会直接检测并退出，不用浪费时间试。

三种装法，挑一种

方式 A：一键脚本（推荐）

Debian 11+ / Ubuntu 22.04+ 上跑，脚本会自动装依赖、建目录、配 systemd、开防火墙、加 Nginx 反代。

shell · 国内服务器（GitCode）
git clone https://gitcode.com/rampump/NTRIPcaster.git && cd NTRIPcaster && sudo bash install.sh
shell · 海外服务器（GitHub）
git clone https://github.com/Rampump/NTRIPcaster.git && cd NTRIPcaster && sudo bash install.sh

脚本干的事：装 python3-venv / nginx / git → 源码放到 /opt/2rtk → 配置放 /etc/2rtk/config.ini → 日志放 /var/log/2rtk → 注册 systemd 服务 2rtk 并设开机自启 → UFW/firewalld 放行 2101/5757 → 写一份 Nginx 配置把 80 端口反代到 5757。

权限说明：普通用户用 sudo bash install.sh；如果本来就是 root 登录（提示符是 #），直接 bash install.sh，不用加 sudo。

方式 B：Docker

不想动系统环境，一条命令起来。国内用腾讯云镜像（不用登录）：

shell · Docker 快速试跑
# 国内（腾讯云镜像，免登录）
docker run -d --name ntrip-caster -p 2101:2101 -p 5757:5757 \
  ccr.ccs.tencentyun.com/2rtk/ntripcaster:latest

# 海外（Docker Hub）
docker run -d --name ntrip-caster -p 2101:2101 -p 5757:5757 \
  2rtk/ntripcaster:latest

正式用建议把三个目录挂出来，数据库和配置就落在宿主机上，删容器不丢数据：

shell · 带持久化
mkdir -p ./ntrip-data/{logs,data,config}

# 先把配置模板抠出来
docker run --rm ccr.ccs.tencentyun.com/2rtk/ntripcaster:latest \
  cat /app/config.ini.example > ./ntrip-data/config/config.ini

docker run -d --name ntrip-caster \
  -p 2101:2101 -p 5757:5757 \
  -v $(pwd)/ntrip-data/logs:/app/logs \
  -v $(pwd)/ntrip-data/data:/app/data \
  -v $(pwd)/ntrip-data/config:/app/config \
  ccr.ccs.tencentyun.com/2rtk/ntripcaster:latest

仓库里还有 docker-compose.yml（开发）和 docker-compose.prod.yml（生产）可以直接用。

方式 C：源码直接跑（不装服务）

只是想在本机或测试机上试一下，用这种方式最快。需要 Python 3.9+：

shell · 源码运行
tar -xzf ntripcaster-full.tar.gz && cd ntripcaster

cp config.ini.example config.ini     # 然后改掉里面的 admin 密码

python3 -m venv venv
source venv/bin/activate
python3 -m pip install -r requirements.txt

python3 main.py

Web 面板在 http://服务器IP:5757，默认账号 admin / admin123。 首次启动会自动生成 data/.secret_key，不用手动填。

装完先验三下

shell · 自检
sudo systemctl status 2rtk            # 服务在跑没
sudo ss -tlnp | grep -E ':2101|:5757' # 两个端口有没有在听
curl -s http://localhost:5757/health  # 期望 {"status":"ok","version":"2.3.4",...}

/health 不需要登录、也不查数据库，Docker 健康检查和监控探活都用它，接 Uptime Kuma 之类的直接填这个地址。

首次登录，先改三处

浏览器打开 http://服务器IP:5757，用 admin / admin123 登进去，然后立刻处理这三件事：

  1. 改管理员密码：界面上直接改。默认账号密码是公开写在文档里的，不改等于没锁门。
  2. 确认 debug_mode = false：生产环境开调试会漏内部信息和堆栈。
  3. 确认 secret_key：留空时程序会自动生成随机值写到 data/.secret_key，不要填成示例值。

配置文件放在哪，取决于你用的是哪种装法：

装法配置文件数据库
一键脚本/etc/2rtk/config.ini/opt/2rtk/data/2rtk.db
Docker/app/config/config.ini/app/data/2rtk.db
源码项目根目录 config.ini2rtk.db

真正需要动的配置项就这么几个，其余保持默认：

[ntrip] port
2101　NTRIP 服务端口，改完记得放行新端口
[web] port
5757　Web 管理端口，和 2RTK Server 冲突时改这里
[database] path
2rtk.db　容器内写 /app/data/2rtk.db 并挂卷
[admin] password
admin123　首次启动创建的管理员口令
[caster] lat / lon
源表的兜底位置，流里没有 1005/1006 时才会用到
[security] 登录限流
5　同一 IP+用户名连错 5 次锁 300 秒

改完配置要重启服务：sudo systemctl restart 2rtk；Docker 用 docker restart ntrip-caster。 环境变量优先级高于配置文件，排查「改了没生效」时先看 systemd unit 里有没有 Environment= 覆盖。

第二步：建用户（拉流账号）

用户是给客户端用的账号，一个客户一个账号，出问题能单独停掉。命名规则卡得比较死：

字段规则
用户名2 – 50 字符，只允许字母、数字、下划线、中横线
密码6 – 100 字符，同样只允许字母、数字、下划线、中横线
保留名不能和管理员同名（admin），否则改密码会改到管理员身上

密码只允许这几类字符，看着别扭，但换来的是不会因为特殊符号在客户端 XML / 命令行里被转义出错。 强度靠长度补：Base01_2026 这种比 a!B2# 好用得多。

密码存的是 PBKDF2 哈希。管理界面只能重设，看不到原值——忘了就让用户改密码，别指望能「查回来」。

第三步：建挂载点

挂载点（mountpoint）就是「一路流」的名字，基站往上推、流动站往下拉，都靠这个名字对上。

挂载点名称
2 – 50 字符，字母 / 数字 / 下划线 / 中横线，例如 BASE01
挂载点密码
6 – 100 字符，NTRIP 1.0 推流和拉流都拿它认证
绑定用户
可选，绑定后 NTRIP 2.0 只允许这个账号推这个点

绑定的作用范围不一样，这点容易踩坑：推流（SOURCE）方向，只要挂载点绑了用户，NTRIP 2.0 就一定校验绑定关系； 拉流方向默认只校验账号密码，任何有效用户都能拉全部挂载点，想收紧得把 [ntrip] download_enforce_user_binding 设成 true。

源表（STR）是自动补的

传统 Caster 要你手写 19 个字段的源表行，格式错一个分号客户端就看不见。这个项目不用： 挂载点建好，基站把 RTCM 推上来后，服务端用 pyrtcm 解析流里的电文， 自动读出坐标、国家、城市和电文类型，再回填到源表里。

  • 位置：从 1005 / 1006 电文取 ECEF 坐标并转成经纬度，反查城市名。
  • 格式与电文：按实际收到的 MSM 电文生成，客户端看到的 GPS+GLO+GAL+BDS 是真的在发，不是抄配置。
  • 兜底：流里没有 1005/1006 时，用 [caster] 里的经纬度；再没有就是模板默认值——所以基站端一定要开 1005/1006。

在挂载点列表里点 STR 前面的 INFO，后台会解析几十秒然后显示出这批电文的明细。 刚推上来的流解析需要点时间，别急着刷。

第四步：让基站把流推上来

Caster 起来只是空壳，挂载点要有源推进来才「活」。推流走 NTRIP 的 SOURCE 请求，两种认证方式：

NTRIP 版本请求行用哪个凭据
1.0（默认）SOURCE <挂载点密码> /<挂载点>挂载点密码
2.0SOURCE /<挂载点> HTTP/1.1 + Basic用户名 + 用户密码

基站侧用 2RTK Server 的话，在 /config 里勾上「上传到上游 Caster」， 填这四项保存即可：

Caster 地址
你的服务器 IP 或域名 caster_host
端口
2101 caster_port
挂载点
BASE01，和网页上建的完全一致 caster_mountpoint
密码
该挂载点的密码（NTRIP 2.0 则填用户账号密码）caster_password

手边没有基站，想先验证链路，可以用 RTKLIB 把一路现成的公共流中继过来：

shell · 中继测试
# 从公共源拉一路，转推到自己的 Caster
str2str -in  "ntrip://user:pass@rtk2go.com:2101/SOME_MOUNT" \
        -out "ntrips://:挂载点密码@caster.example.com:2101/BASE01"

推上去后回首页看：Mount Point Details 里该挂载点变成 online，Data Packets 一直在涨，就说明通了。

挂载点必须先建。Caster 不会因为收到一路新流就自动创建挂载点，名字对不上直接拒绝。 日志里出现「挂载点不存在」就是这个问题，不是密码错。

第五步：流动站怎么连

手簿 / App / 接收机里选 NTRIP，填这几项：

Caster 地址
caster.example.com
端口
2101
挂载点
BASE01
用户名 / 密码
网页上建的用户账号（NTRIP 2.0）
NTRIP 版本
优先选 2.0；老设备只有 1.0 时改用挂载点密码

认证方式跟版本绑死，选错了就会一直 401：

客户端支持的版本要填什么
NTRIP 2.0用户名 + 用户密码（挂载点密码在这里不起作用）
NTRIP 1.0 / 0.9挂载点密码，用户名随便填或留空

只支持 Basic，Digest 已经整个移除。早期版本留过 Digest 实现但从没真正校验过 nonce， 现在收到 Digest 请求会回 401 并只声明 Basic。如果你的客户端被设成 Digest 认证，会连不上，改成 Basic 或换 NTRIP 2.0。

连上后先收到 ICY 200 OK（1.0）或 HTTP/1.1 200 OK（2.0），紧接着就是一串二进制 RTCM。 能连但久久不出固定解，八成是电文不匹配——回挂载点列表点 INFO，看实际发的电文里有没有你的接收机需要的类型。

升级、备份与回滚

在源码目录里跑，不要在 /opt/2rtk 里跑。/opt/2rtk/update.sh 是安装时留下的一份旧拷贝，永远不自我更新。

shell · 升级
cd ~/NTRIPcaster          # 当初 clone 的目录
git pull                  # 先把 update.sh 自己更新到最新
sudo bash update.sh

update.sh 会自动判断你是一键脚本装的还是 Docker 装的，然后：

  • 备份 config.ini 和数据库；
  • 找到真正在跑的那个 systemd 服务（哪怕你改过单元名），stop 掉，25 秒还没停就 SIGKILL；
  • 顺手杀掉手工 python main.py 起的野进程，等 2101 / 5757 真的空出来；
  • 替换代码 → 起服务 → 健康检查；失败就用备份回滚。

Docker 部署同理：先 stop 再 rm -f 再 up -d --force-recreate。跳过删除这一步，就会出现 container name is already in use，或者旧容器继续占着 2101/5757。

shell · 强制更新 / 指定源
sudo bash update.sh --force              # 不比版本，直接更
sudo REPO_SOURCE=github bash update.sh   # 源码模式走 GitHub
sudo REPO_SOURCE=gitcode bash update.sh  # 源码模式走 GitCode
sudo REPO_SOURCE=tcr bash update.sh      # Docker 模式走腾讯云镜像

源码目录删了也能救——临时拉一份新的再跑：

shell · 没有源码目录
cd /tmp && rm -rf _2rtk_upd
git clone --depth 1 https://gitcode.com/rampump/NTRIPcaster.git _2rtk_upd
sudo bash _2rtk_upd/update.sh
rm -rf /tmp/_2rtk_upd

备份只要两个文件

文件内容
/etc/2rtk/config.ini端口、管理员口令、密钥、各类参数
/opt/2rtk/data/2rtk.db全部用户、挂载点、密码哈希

这两个拷走，换台机器重装一遍再放回去，账号和挂载点原样还在。日志不用备。

安全清单

  • 改掉 admin 默认密码——文档里公开写着的口令，等于没有。
  • 只开两个端口：2101 给 NTRIP，5757 给管理。SSH 别和面板一起暴露在 0.0.0.0。
  • 管理端口不要裸奔公网：用 Nginx 反代到 443 加 HTTPS，再套一层 Basic 认证或限制来源 IP。
  • 一个客户一个账号：停服务时只停一个人，不用改全局密码。
  • 收紧拉流范围：多客户多基站时，把 download_enforce_user_binding 打开，只允许拉自己绑定的点。
  • 登录限流保持默认：5 次失败锁 300 秒，别为了省事关掉。
  • 盯住 /health：定时 curl 一下，非 200 就告警。

套了反向代理记得改两个开关：[security] trust_proxy_headers = true 才会信任 X-Forwarded-For（否则日志里全是 127.0.0.1）；上了 HTTPS 再开 session_cookie_secure = true。 另外 [websocket] cors_allowed_origins 跨域时写死白名单，不要用 *。
